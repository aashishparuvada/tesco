02Why the layers exist

The medallion pattern is not decoration. Each layer answers a different question, and mixing them is how pipelines become impossible to debug.

Source

raw_data in Postgres

The operational database. Types are permissive, only primary keys are NOT NULL. A landing layer that rejects rows loses data you cannot get back.

Bronze

A faithful replica

What CDC lands in Databricks. Same grain, same values, plus history. No business logic whatsoever — if bronze disagrees with the source, something is broken.

Silver

Conformed and joined

Incremental dbt models that merge on the primary key, plus one wide table joining all six so an analyst never writes a six-way join by hand.

Gold

A star schema

Five Type 2 dimensions that remember what a value used to be, and one fact table at order-item grain. This is what a dashboard actually points at.

01The three audit columns

Every one of the six tables carries the same three trailing columns. They look like boilerplate. They are the reason the free path through this project works at all.

  • created_timestampWhen the row first appeared. Rarely used downstream, but it is what lets you separate "new customer" from "customer who changed address".
  • updated_timestampWhen the row last changed. This is the sequencing column: it tells Databricks which of two versions of the same row is newer, and it is the watermark every incremental dbt model compares against.
  • is_activeA Y/N soft-delete flag. A deleted row is not removed, it is marked. That turns a delete — normally invisible to anything reading a table — into an ordinary row change that a query can see.

Remember this when you reach step 6

Real CDC reads a database's write-ahead log, which requires network access most free tiers will not give you. These three columns let you get the same semantics — ordered changes, and deletes that propagate — from a plain SELECT. They are a deliberate design decision, not incidental metadata.

02Is any of this real?

No, and deliberately so. Phone numbers use the Ofcom-reserved drama ranges (07700 900xxx, 020 7946 0xxx, 01632 960xxx), every email uses an example.* domain, and monetary values read as GBP. No value corresponds to a real person or line, so the whole dataset is safe to commit, fork and publish.

The retail theme is a costume. This is an independent learning project, not affiliated with or endorsed by any retailer.

01Get the connection string right

This is where nearly everyone loses an hour on Supabase, so it is worth understanding rather than copying. The URI shown most prominently in the dashboard is the direct connection:

postgresql://postgres:[YOUR-PASSWORD]@db.<project-ref>.supabase.co:5432/postgres

That hostname resolves to an IPv6 address only:

terminalbash
$ dig +short AAAA db.<project-ref>.supabase.co
2406:da14:1d62:b401:4281:9d41:890f:b5b0

$ dig +short A db.<project-ref>.supabase.co
                                    # nothing at all

On an IPv4-only network that fails with could not translate host name ... to address. The fix is the Session pooler URI, from Project Settings → Database → Connection string. Two things change:

FieldDirect — does not connectSession pooler — use this
Hostdb.<project-ref>.supabase.coaws-<n>-<region>.pooler.supabase.com
Userpostgrespostgres.<project-ref>
Port54325432 (session), not 6543

Both the aws-<n>- prefix and the region are per-project. Copy them from the dashboard, do not guess.

Prefer session mode on port 5432 over transaction mode on 6543: the loader bulk-copies inside a single transaction, which session mode handles without caveats.

02Put it in .env

.envenv
SUPABASE_CONNECTION_STRING=postgresql://postgres.YOUR_PROJECT_REF:{SUPABASE_DB_PASSWORD}@aws-0-YOUR_REGION.pooler.supabase.com:5432/postgres
SUPABASE_DB_PASSWORD=your_database_password

Leave the {SUPABASE_DB_PASSWORD} placeholder literal

It is not a typo and not a shell variable. build_dsn() substitutes it at runtime and percent-encodes the value, so the password lives in exactly one place and a @, # or / in it cannot break URL parsing. Two other things happen there: sslmode=require is appended if absent — psycopg2 would otherwise merely prefer TLS and can silently fall back to plaintext — and a 10-second connect timeout is added so a wrong host fails fast instead of hanging.

Verify

Connect by hand before involving the loader — a failure here is a credentials problem, a failure later is a code problem, and you want to know which you have:

01What the loader actually does

This is the part worth understanding, because it is the reusable idea — and because it is one file, scripts/python/loader.py, that both the local and hosted entry points share so they cannot drift apart.

  • 1 · DiscoveryEvery *.csv in data/ becomes a table named after the file. Adding a CSV is the only step needed to get a new table — there is no registry to update.
  • 2 · ProfilingEach file is read once, recording per column whether every value parses as an integer, decimal, timestamp or date, plus the longest value, the largest integer, the maximum numeric scale and the distinct count.
  • 3 · Type inferenceThe narrowest type that still fits every value observed — see the ladder below.
  • 4 · Key detectionA leading *_id column that is unique and never empty becomes the PRIMARY KEY. Nothing else gets a constraint.
  • 5 · ExecutionCREATE SCHEMA IF NOT EXISTS raw_data, then DROP TABLE IF EXISTS + CREATE TABLE per table, then COPY ... FROM STDIN — the fastest path into Postgres, far faster than row-by-row INSERT.
  • 6 · VerificationEvery table is re-counted after loading and the run fails if the count does not match the source CSV.
The type-inference ladder, in priority orderdeep dive

sql_type() walks this list top to bottom and takes the first type that fits every value it profiled:

TypeChosen when
TIMESTAMPEvery value parses against one of the known timestamp formats
DATEEvery value parses as a date but none carries a time
BIGINTAll integers, and the column is named *_id or exceeds int32
INTEGERAll integers within int32
NUMERIC(p, s)All decimals — precision gets +4 headroom over what was observed
CHAR(1)Maximum length is exactly one character (this is what is_active lands as)
VARCHAR(n)Rounded up to the next bucket: 10, 20, 50, 100, 255, 500, 1000, 4000
TEXTLonger than the largest bucket

The headroom is deliberate. A column whose longest value today is 18 characters becomes VARCHAR(20), not VARCHAR(18), so a slightly longer value in next month's extract does not break the load.

The result is written to scripts/sql/raw_data/ddl.sql and committed, so a schema change shows up in code review instead of drifting silently:

scripts/sql/raw_data/ddl.sqlgenerated
CREATE TABLE raw_data.customers (
    customer_id BIGINT PRIMARY KEY,
    first_name VARCHAR(20),
    last_name VARCHAR(20),
    email VARCHAR(100),
    phone VARCHAR(50),
    city VARCHAR(50),
    province VARCHAR(50),
    country VARCHAR(50),
    created_timestamp TIMESTAMP,
    updated_timestamp TIMESTAMP,
    is_active CHAR(1)
);

Never hand-edit that file. To change the schema, change the inference rules in loader.py and re-run the loader to regenerate it.

02Three properties worth stealing

Atomic

One transaction

Schema creation, every CREATE TABLE, every COPY and the row-count check all commit together. A failure at table five leaves the database exactly as it was. There is no half-loaded state to clean up, so re-running is always safe.

Safe

Identifiers are validated

Table and column names must match a lower-snake-case pattern or the run aborts, and they are interpolated through psycopg2.sql rather than f-strings. A CSV filename cannot become SQL injection.

Quiet

Passwords never reach the logs

redact() rebuilds the connection URI without its password before anything is printed. Preserve that if you touch the logging — a pasted terminal transcript is a very common leak.

Why raw_data is so permissive

Only primary keys are NOT NULL. Everything else stays nullable and accepts whatever the source sends. That is not laziness — it is the definition of a landing layer. Constraints, conformed types and business rules belong downstream, where a rejected row can be investigated instead of lost. A raw layer that rejects rows destroys data you cannot get back.

Bronze · Step 6

What CDC is, why it matters, and the two walls you will hit

Read this before you build anything. Both walls are documented vendor limits rather than bugs, and knowing them now saves an afternoon.

01The problem CDC solves

The naive way to keep Databricks in sync is to re-export all 42,796 rows every night and overwrite the target. That works perfectly here, and stops working immediately at real scale, because the cost grows with table size rather than with how much actually changed. A billion-row table where fifty rows moved yesterday still costs you a billion rows of read and write.

Change Data Capture reads the changes themselves. Postgres already writes every insert, update and delete into its write-ahead log for durability. Logical replication lets an external consumer subscribe to that log, so Databricks receives "customer 1,432 changed city" instead of re-reading two thousand customers.

The part people miss: deletes

A WHERE updated_timestamp > last_run query can never see a delete. The row is simply gone, and "gone" produces no row to select. This is the single strongest argument for real CDC — and the reason this dataset carries an is_active flag, which turns a delete into a row change a query can see.

02How Databricks implements it

Lakeflow Connect's PostgreSQL connector uses logical replication with the pgoutput plugin, and splits the work across two pipelines:

  • an ingestion gateway that continuously reads the WAL into staging storage;
  • an ingestion pipeline that applies those changes into Delta tables.

The most important operational fact about CDC

The gateway must run continuously. If it stops, Postgres keeps retaining WAL segments for your unconsumed replication slot — forever — until the source disk fills and the database stops accepting writes. Stopping a consumer and forgetting about it is the most common way people take down the very database they were trying to replicate.

03Blocker 1 — Free Edition cannot run the managed connector

The Lakeflow Connect docs state that the ingestion gateway runs on classic compute inside your workspace VPC. Free Edition provides serverless compute only. Put together: log-based CDC through the managed connector needs a paid or trial workspace.

Databricks does not state that combination explicitly in one place, so verify it against current docs before spending money — previews change.

04Blocker 2 — Supabase free cannot carry a replication connection

Two independent reasons, both from Supabase's own docs:

  1. Logical replication needs a direct connection. Connections through Supavisor, the pooler, will not work for replication — and on a free project the pooler is the only IPv4 route in.
  2. The direct host is IPv6-only. Reaching it over IPv4 requires the IPv4 add-on, which needs at least the Pro plan.

The database itself is perfectly ready: a free Supabase project already reports wal_level = logical, Postgres 17.6 and five available replication slots. This is purely a network-reachability wall, which is exactly why it is so confusing to debug.

Bronze · Step 7

Build bronze with AUTO CDC

Register your Postgres as a foreign catalog, then let Databricks apply inserts, updates and deletes into streaming tables — with full history.

This runs entirely on Databricks Free Edition and needs nothing from your Postgres beyond a normal SQL login. The pooler is fine here, because this is not replication — it is a query.

01Register the connection

Query federation lets Unity Catalog treat a remote database as if it were part of the catalog. Note the secret() calls — the scope you created in step 5:

Databricks SQL editorsql
CREATE CONNECTION supabase_pg TYPE postgresql OPTIONS (
  host 'aws-0-<region>.pooler.supabase.com',
  port '5432',
  user secret('tesco', 'pg_user'),
  password secret('tesco', 'pg_password')
);

CREATE FOREIGN CATALOG tesco_source USING CONNECTION supabase_pg
  OPTIONS (database 'postgres');

tesco_source.raw_data.customers is now queryable from Databricks without copying a single byte. Nothing has been ingested yet — every query against it reaches across the network to Postgres and back.

Verify

Databricks SQL editorsql
SELECT count(*) FROM tesco_source.raw_data.order_items;
30021

A connection error here is almost always the unverified account from step 5, not your credentials.

02Apply the changes

The AUTO CDC APIs — which replace APPLY CHANGES with identical syntax — handle out-of-order events, deletes, and SCD Type 1 and 2 for you. Create this as a pipeline, and put all six tables in the same one:

pipeline sourcesql
CREATE OR REFRESH STREAMING TABLE bronze.customers;

CREATE FLOW customers_cdc AS AUTO CDC INTO bronze.customers
FROM stream(tesco_source.raw_data.customers)
  KEYS (customer_id)
  APPLY AS DELETE WHEN is_active = 'N'
  SEQUENCE BY updated_timestamp
  COLUMNS * EXCEPT (is_active)
  STORED AS SCD TYPE 2;

Read that clause by clause, because every line is doing real work:

  • KEYS (customer_id)The identity of a row. Two records with the same key are two versions of the same thing, not two things.
  • SEQUENCE BY updated_timestampWhich version wins. Without it, an event that arrives late would overwrite a newer one — and events do arrive out of order.
  • APPLY AS DELETE WHENTurns the soft-delete flag into a real delete in the target. This is why the source carries is_active.
  • COLUMNS * EXCEPT (is_active)The flag was a transport mechanism, not data. Once its meaning has been applied it does not belong in bronze.
  • STORED AS SCD TYPE 2Keep history rather than overwriting. You can ask what a customer's city was last month — the question a nightly overwrite permanently destroys. Use SCD TYPE 1 if you only want current state.

Repeat the pair of statements for orders, order_items, products, employees and stores, changing only the table name and the key.

One pipeline, not six

Free Edition allows one active pipeline per pipeline type. Six separate pipelines will not run concurrently — build one that handles all six tables.

Verify — and prove it actually captures change

Counts first:

Databricks SQL editorsql
SELECT count(*) FROM tesco.bronze.customers;    -- expect 2,000
SELECT count(*) FROM tesco.bronze.order_items;  -- expect 30,021

Counts only prove the first load worked. Now change a row at the source and watch it propagate — this is the actual test of the pipeline:

Postgres — the sourcesql
UPDATE raw_data.customers
SET city = 'Manchester', updated_timestamp = now()
WHERE customer_id = 1;

Re-run the pipeline, then query bronze for that customer. With SCD TYPE 2 you should see two rows for customer_id = 1: the old city with a closed validity window, and Manchester as the current version. One row means you built Type 1; zero changes means the pipeline did not re-run.

The real thing: Postgres streams its write-ahead log and Databricks applies it. Needs a source that serves logical replication over a network Databricks can reach, and a workspace with classic compute. Full walkthrough in the Databricks docs; the source-side setup is:

Postgres — the sourcesql
-- 1. Confirm logical replication is on (Supabase/Neon: already 'logical')
SHOW wal_level;

-- 2. A dedicated replication role
CREATE USER databricks_replication WITH PASSWORD '<strong-password>';
GRANT CONNECT ON DATABASE postgres TO databricks_replication;
GRANT USAGE ON SCHEMA raw_data TO databricks_replication;
GRANT SELECT ON ALL TABLES IN SCHEMA raw_data TO databricks_replication;
ALTER USER databricks_replication WITH REPLICATION;

-- 3. Replica identity: DEFAULT is fine, every table here has a primary key
ALTER TABLE raw_data.customers REPLICA IDENTITY DEFAULT;
-- ... repeat per table, or use FULL for tables without a PK

-- 4. Publication -- the set of tables to replicate
CREATE PUBLICATION databricks_publication FOR TABLE
    raw_data.stores, raw_data.employees, raw_data.customers,
    raw_data.products, raw_data.orders, raw_data.order_items;

-- 5. Replication slot -- the consumer's bookmark into the WAL
SELECT pg_create_logical_replication_slot('databricks_slot', 'pgoutput');

Then, in Databricks: create a Unity Catalog connection of type postgresql, create the ingestion gateway pipeline, and create the ingestion pipeline, naming databricks_slot and databricks_publication.

Supabase: use the session pooler here too

The Databricks PostgreSQL connector simply fails to connect if you give it the direct host, for the same IPv4/IPv6 reason as step 3. Use host aws-<n>-<region>.pooler.supabase.com with user postgres.<project-ref> on port 5432.

But a green connection test is not a working replication. Supabase documents that logical replication does not pass through Supavisor, so the gateway can still fail at the replication step after the connection tests fine. The supported routes from there are the IPv4 add-on on the Pro plan, or a source like Neon that serves replication over IPv4 for free.

Operational rules, all from the vendor docs

  • Keep the gateway running continuously, or WAL accumulates on the source until the disk fills.
  • Deleting a pipeline does not drop the replication slot. Drop it yourself with pg_drop_replication_slot('databricks_slot') or it retains WAL forever.
  • Replication works only against a primary instance, never a read replica.
  • Neon removes replication slots that have been inactive for roughly 40 hours.

Once bronze exists, everything from step 8 onwards is identical to Path B. The rest of this guide does not care how the rows arrived.

Silver · Step 8

Connect dbt to Databricks

Four things stand between a fresh machine and a passing dbt debug: a version pin the adapter forces on you, a scaffolding quirk, where credentials live, and one certificate problem that will waste your afternoon if you do not recognise it.

terminalbash

cd dbt

01Pin dbt-core below 1.12, or resolution fails

Installing the two packages without a constraint does not work:

terminalbash
uv add dbt-core dbt-databricks          # fails to resolve

dbt-databricks trails dbt-core by design. Version 1.12.4 declares:

Requires-Dist: dbt-core<1.12.1,>=1.11.2
Requires-Dist: dbt-spark<1.11.0,>=1.10.0

Unconstrained, the resolver reaches for the newest dbt-core on PyPI — outside that range. The working install, and what pyproject.toml records:

terminalbash
uv add "dbt-core<1.12" dbt-databricks

which resolves to dbt-core 1.11.14, dbt-databricks 1.12.4, dbt-spark 1.10.3.

dbt --version will tell you dbt-core is out of date. Ignore it.

That warning compares against PyPI, not against what your adapter supports. Upgrading to satisfy it breaks the adapter. Do not pin downwards either — dbt-core<=1.7 also fails, because 1.11.2 is the floor dbt-databricks 1.12.4 accepts. The usable window is narrow: >=1.11.2,<1.12.1.

02Scaffold the project, then flatten it

Only relevant if you are building this from scratch rather than cloning the repo — but it explains why dbt/ looks the way it does.

dbt init will not initialise a project inside an existing directory; it always creates a subdirectory named after the project. Run from dbt/, it gives you dbt/tesco/ — one level deeper than you want. The prompts are: adapter (databricks), workspace host, SQL warehouse HTTP path, access token, catalog (tesco), schema (dbt_schema), threads (1).

terminalbash
cd dbt
uv run dbt init                 # project name: tesco  ->  creates dbt/tesco/
mv tesco/* tesco/.[!.]* .       # the dotfiles matter - .gitignore is one of them
rmdir tesco                     # refuses to run if anything was left behind

Use rmdir, not rm -rf. It fails loudly if the move missed a file, which is exactly what you want: dbt init writes a .gitignore into the project root and a plain mv tesco/* . silently leaves it behind.

03Where profiles.yml lives

dbt init writes your credentials to ~/.dbt/profiles.yml, outside the repo. This project keeps them next to the dbt project instead, so the whole setup is visible in one tree:

  • dbt/profiles.yml — your real host, HTTP path and token. Git-ignored.
  • dbt/profiles.yml.example — the same file with placeholders, committed.
terminalbash
cp dbt/profiles.yml.example dbt/profiles.yml
dbt/profiles.ymlyaml

04The certificate error, and the one command that fixes it

On macOS with a python.org (framework) Python, TLS fails twice — once while installing packages, once on dbt debug — and the two look like unrelated problems. They are the same problem, and it is neither dbt's fault nor your network's.

Symptom 1, installing. A certificate error while fetching from PyPI: expired, unable to verify, or self-signed in chain, depending on which tool reports it.

Symptom 2, dbt debug. Every configuration check passes, then the connection test blows up:

Registered adapter: databricks=1.12.4
...
  File ".../python3.12/ssl.py", line 1320, in do_handshake
    self._sslobj.do_handshake()
ssl.SSLCertVerificationError: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify
failed: self-signed certificate in certificate chain (_ssl.c:1000)

dbt debug can sit there for fifteen minutes before showing you any of that

databricks-sql-connector treats the failed handshake as retryable and works through its retry policy first:

Error during request to server. Retry request would exceed Retry policy
max retry duration of 900.0 seconds
Error properties: attempt=1/30, elapsed-seconds=858.7/900.0, method=OpenSession

If dbt debug hangs on "Opening a new connection", do not wait it out. Ctrl-C and check your certificate store.

The cause

The python.org installer ships no CA bundle at all until you run its post-install script. The interpreter has nothing to validate any chain against, and OpenSSL reports that missing trust anchor as "self-signed certificate in certificate chain" — which sends everybody hunting for a corporate proxy that does not exist. Two commands confirm it:

terminalbash
ls -l /Library/Frameworks/Python.framework/Versions/3.12/etc/openssl/
# empty - there is no cert.pem

uv run python -c "import ssl; print(ssl.get_default_verify_paths())"
# openssl_cafile='/Library/Frameworks/.../etc/openssl/cert.pem'  <- does not exist

A venv built from that interpreter inherits the problem, which is why uv and dbt fail identically. curl and your browser keep working because they use the system keychain rather than Python's store — and that asymmetry is exactly what makes it look like a dbt bug.

The fix

terminalbash
open "/Applications/Python 3.12/Install Certificates.command"

It pip-installs certifi into the framework Python and symlinks the missing store at it. (pip carries its own bundled certificates, so it works even while the store is broken.)

Do not set SSL_CERT_FILE in your shell profile

One run of that script repairs every venv, every project and every tool on the machine — including VS Code, whose extension host never reads ~/.zshrc and so cannot see a terminal-only workaround anyway. export SSL_CERT_FILE=... will get a single command working in a pinch, but as a permanent fix it is a trap: pointing it at a path inside a project's .venv makes every Python program on your machine depend on that venv, and rebuilding .venv then breaks them all in unrelated places. Fix the interpreter and set nothing.

Verify

terminalbash
ls -l /Library/Frameworks/Python.framework/Versions/3.12/etc/openssl/cert.pem
cd dbt && uv run dbt debug
cert.pem -> ../../lib/python3.12/site-packages/certifi/cacert.pem

Connection:
  host: <your-workspace>.cloud.databricks.com
  http_path: /sql/1.0/warehouses/<id>
  catalog: tesco
  schema: dbt_schema
  Connection test: [OK connection ok]

All checks passed!

Do not continue past this. Every later step assumes dbt can reach the warehouse, and a failure at step 11 caused by a broken connection here looks nothing like a connection problem.

Optional: VS Code and the dbt Power User extensionoptional

dbt on its own is a CLI. dbt Power User makes it usable in an editor: compiled-SQL preview beside the model you are editing, a lineage graph built from your ref() calls, go-to-definition across models, column-level autocomplete, and run/test buttons per model. None of it is required — every command here is CLI-first — but on a Jinja-heavy model layer it saves a lot of dbt compile && cat target/....

Installing it pulls in three dependencies automatically: samuelcolvin.jinjahtml (Jinja-aware SQL highlighting), ms-python.python (supplies the interpreter), and altimateai.vscode-altimate-mcp-server (optional AI features, harmless if unused).

The one thing you must get right is the interpreter. The extension does not bundle dbt — it shells out to whichever Python the Python extension has selected, so that interpreter has to be the one holding dbt-core. Here that is the venv at the repo root, one level above the dbt project. .vscode/settings.json is committed and already points at it:

.vscode/settings.jsonjson

  "python.defaultInterpreterPath": "${workspaceFolder}/.venv/bin/python",
  "files.associations": { "dbt/**/*.sql": "jinja-sql" },

Fix the certificate store before you trust this extension's error messages. It runs dbt itself, so a broken trust store surfaces here as a failed connection, a stalled lineage graph, or a query preview that never returns — with no terminal output to explain why.

Silver · Step 9

Silver: six incremental models that merge instead of append

Same shape six times over. Understand one of them and you understand the whole layer — including the one-line mistake that makes an incremental model silently load nothing.

If bronze does not exist yet

These models read from tesco.bronze. Until step 7's pipeline has landed those tables, dbt run fails with "Table or view not found" — that is expected, not a broken model. dbt parse and dbt compile work regardless, so you can develop and review all of the SQL before the data exists.

01Declare the sources, do not hard-code the catalog

dbt/models/source/sources.ymlyaml
sources:
  - name: tesco_databricks
    database: tesco
    schema: bronze
    tables:
      - name: orders
      - name: customers
      - name: products
      - name: order_items
      - name: employees
      - name: stores

Every model then reads {{ source('tesco_databricks', 'orders') }} rather than tesco.bronze.orders. Two things fall out of that: dbt now knows bronze is upstream, so dbt run --select source:tesco_databricks+ and the lineage graph work — and if bronze ever moves catalog or schema, it moves in this one file instead of in six.

02One model, four decisions

dbt/models/silver/customers.sqlsql · jinja
{{
  config(
        materialized = 'incremental',
        incremental_strategy = 'merge',
        unique_key = 'customer_id'
    )
}}

SELECT
    *,
    CURRENT_TIMESTAMP() AS processed_at
FROM
    {{ source('tesco_databricks', 'customers') }}

{% if is_incremental() %}

    WHERE updated_timestamp > (
        SELECT
            COALESCE(
                MAX(updated_timestamp),
                '1900-01-01'
            )
        FROM {{ this }}
    )

{% endif %}

The other five differ only in the source table and the unique_key: order_id, product_id, order_item_id, employee_id, store_id.

materialized = 'incremental'

On the first run — or any run with --full-refresh — dbt creates the table from the full SELECT. On every run after that it runs the same SELECT and merges the result into the existing table. You are not rebuilding 30,000 order lines to pick up yesterday's changes.

incremental_strategy = 'merge' with a unique_key

The default strategy would append, which turns every update into a duplicate row. merge compiles to a Delta MERGE INTO ... ON target.customer_id = source.customer_id, so a changed row updates in place and a new one inserts. This is what makes an incremental model idempotent: re-running it after a partial failure converges instead of doubling.

The is_incremental() watermark

The WHERE clause only exists on incremental runs — on a full refresh the block is not rendered at all, because {{ this }} does not yet hold anything to compare against. When it does render, it limits the scan to rows whose updated_timestamp is newer than the newest one already in the target. That is what turns "merge the whole table every time" into "merge only what moved".

Why COALESCE(..., '1900-01-01') is not optional

On the first incremental run after a full refresh the target can be empty, and MAX(updated_timestamp) over an empty table returns NULL. updated_timestamp > NULL is not false — it is NULL, which filters out every single row, and the model silently loads nothing.

The sentinel date guarantees the comparison is always against a real value. This is the most common way a hand-written incremental model quietly does nothing, and it produces no error to tell you.

processed_at is stamped with CURRENT_TIMESTAMP() on the way through, so every silver row records when dbt touched it — distinct from created_timestamp / updated_timestamp, which describe when the source row changed. The is_active flag is carried through untouched: silver is still a faithful copy, and deciding what a soft-deleted row means is a gold-layer concern.

03The macro that stops dbt renaming your schemas

dbt_project.yml routes the models to a silver schema:

dbt/dbt_project.ymlyaml
models:
  tesco:
    silver:
      +materialized: table
      +schema: silver

By default that does not produce a schema called silver. dbt's built-in generate_schema_name concatenates, so +schema: silver against a target schema of dbt_schema gives you dbt_schema_silver. That behaviour exists so several developers can build into one warehouse without colliding, and it is exactly wrong for a medallion layout where bronze, silver and gold are fixed names in the catalog.

dbt/macros/custom_schema.sqljinja
{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- set default_schema = target.schema -%}
    {%- if custom_schema_name is none -%}
        {{ default_schema }}
    {%- else -%}
        {{ custom_schema_name | trim }}
    {%- endif -%}
{%- endmacro %}

A model with no +schema still lands in the target schema from profiles.yml; a model with one lands in exactly that schema, verbatim. dbt picks the macro up by name — there is nothing to register.

Verify — before you run anything expensive

Compiling touches no warehouse, so this works even if bronze is not built yet:

terminalbash
cd dbt
uv run dbt compile
head -3 target/run/tesco/models/silver/customers.sql
create or replace table `tesco`.`silver`.`customers`

If you see tesco.dbt_schema_silver.customers instead, the macro is not being picked up — check it is in dbt/macros/ and that the macro name is spelled exactly generate_schema_name.

Then, once bronze exists:

terminalbash
uv run dbt run --select silver --exclude obt
Completed successfully
Done. PASS=6 WARN=0 ERROR=0 SKIP=0 TOTAL=6

After you edit a silver model, full-refresh it

dbt run on a model whose SQL you just changed will merge into the old table, because incremental models do not notice that their own definition moved. Run uv run dbt run --full-refresh --select customers. Forgetting this is why a column you just added shows up empty.

Silver · Step 10

The OBT: declare the joins as data, generate the SQL

One wide table so an analyst never writes a six-way join. Written by hand that is seventy aliased columns and five LEFT JOINs that drift out of sync. Written as a loop, adding a dimension is one dictionary.

dbt/models/silver/obt.sqlsql · jinja
{% set configs = [
    {
        "model": "orders",
        "columns": """o.order_id,
    o.store_id,
    o.order_timestamp,
    o.payment_method,
    o.order_status,
    o.total_amount,
    o.created_timestamp AS order_created_timestamp,
    o.is_active AS order_is_active""",
        "alias": "o"
    },
    {
        "model": "customers",
        "columns": """c.customer_id,
    c.first_name AS customer_first_name,
    c.city AS customer_city""",
        "alias": "c",
        "join_condition": "o.customer_id = c.customer_id"
    }
    -- ... order_items, products, employees, stores
] %}

SELECT
{% for cfg in configs %}
    {{ cfg['columns'] }}{% if not loop.last %},{% endif %}
{% endfor %}
FROM
{% for cfg in configs %}
    {% if loop.first %}
        {{ ref(cfg['model']) }} AS {{ cfg['alias'] }}
    {% else %}
    LEFT JOIN
        {{ ref(cfg['model']) }} AS {{ cfg['alias'] }}
        ON {{ cfg['join_condition'] }}
    {% endif %}
{% endfor %}

The first entry is the anchor and gets no join_condition; every other entry contributes one LEFT JOIN. The column list and the join list cannot fall out of sync, because they are the same object.

01Why ref() matters more than it looks

The tables come from ref(), not hard-coded names. dbt builds its DAG by instrumenting ref() during the parse phase: every call is recorded as an edge and returns a Relation that renders to the fully-qualified name. Because the {% set %} block and the loop always evaluate, a ref() buried inside a loop over a dict registers exactly as a top-level one would.

Consequence 1

dbt orders the build for you

dbt run builds the six silver models before the OBT. dbt build --select +obt selects the whole upstream chain. Hard-coded names produce an orphan node that dbt will happily build first, against yesterday's data.

Consequence 2

It resolves per target

tesco.silver.orders written out literally means a dev run building into tesco.dev_silver still reads production silver — silently, with no error. ref() goes through the same schema macro, so dev reads dev.

One cost, worth knowing and not worth avoiding: ref() with a variable argument defeats dbt's fast static parser, so this model falls back to full Jinja rendering at parse time. That is milliseconds, and it changes nothing about the compiled SQL.

Verify the edges actually registered

A ref() that never renders produces no error — just a silently orphaned node. So check the DAG rather than trusting the SQL. This touches no warehouse:

terminalbash
cd dbt
uv run dbt ls --select +obt --resource-type model --output name

The + prefix means "this node and everything upstream of it". If ref() is wired up, all six silver models come back alongside the OBT:

customers
employees
obt
order_items
orders
products
stores

If it prints obt on its own, the model is an orphan and dbt is free to build it before the tables it reads.

02Two details in the column lists

  • Collisions are aliased by entitycustomers, employees and stores all have a city; two have an email and a first_name. They come out as customer_city / store_city, customer_email / employee_email. Without this the model fails to build — or worse, builds with ambiguous duplicates.
  • Audit columns survive the flatteningEach entity's created_timestamp, updated_timestamp, is_active and processed_at are carried through prefixed, and the last entry adds CURRENT_TIMESTAMP() AS obt_processed_at. A wide table that has lost its provenance cannot be reconciled against bronze; this one can.

The joins are LEFT on purpose

An order line whose product row has not replicated yet should still appear in the OBT with NULL product columns, rather than vanishing from the analysts' table because of a race in the CDC feed. That choice is exactly what the next step's singular test exists to police.

Two small traps in this filedeep dive

The loop variable is cfg, not config, deliberately. config is dbt's own context object; shadowing it inside the loop would break any later {{ config.get(...) }} in the same block, in a way that is genuinely hard to spot.

The lineage graph is generated, not committed. target/ — where dbt ls and dbt compile write manifest.json — is git-ignored, same as dbt_packages/ and logs/. Cloning the repo does not hand you a lineage graph; it hands you the ref() calls the graph is built from. Regenerate it locally:

terminalbash
cd dbt
uv run dbt docs generate    # writes target/manifest.json + target/catalog.json
uv run dbt docs serve       # lineage graph at localhost:8080

docs generate needs a live warehouse connection to fill in catalog.json, unlike dbt ls and dbt compile which are connection-free.

Silver · Step 11

Two kinds of test, and knowing which failure should stop the build

dbt has exactly two testing shapes. The interesting decision is not writing them — it is choosing whether a failure is an error or a warning.

01Generic tests, declared in YAML

dbt/models/silver/properties.ymlyaml
models:
  - name: products
    columns:
      - name: product_id
        data_tests:
          - not_null
          - unique:
              config:
                where: "price > 0"

  - name: orders
    columns:
      - name: order_id
        data_tests:
          - not_null
          - unique

The where on the products uniqueness check is worth noticing. It scopes the test to priced rows — which is how you assert a rule that genuinely only holds for part of a table, without either weakening it everywhere or failing the run on rows it was never meant to cover.

02Singular tests, which are just a query

A singular test is a SELECT that should return no rows. Any row it returns is a failure. This one checks that the OBT's keys all survived their joins:

dbt/tests/test_obt.sqlsql · jinja
{{ config(severity='warn') }}

SELECT 1
FROM
    {{ ref('obt') }} AS obt
WHERE
    obt.order_id IS NULL
    OR obt.product_id IS NULL
    OR obt.customer_id IS NULL
    OR obt.order_item_id IS NULL
    OR obt.employee_id IS NULL
    OR obt.store_id IS NULL

severity='warn' is the whole point of this test

Because the joins are LEFT, a NULL key means a real referential gap in the source data — an order whose customer has not arrived, an order line pointing at a deleted product. You want to know that. You do not want it to fail the build and block every downstream model, because mid-replication the gap may well be legitimate. Warn, look, then decide.

03Run them

terminalbash
cd dbt
uv run dbt run     # build silver, then the OBT
uv run dbt test    # generic + singular tests
uv run dbt build   # or: run and test model by model, in DAG order

dbt build is usually what you want day to day — it tests each model as soon as it is built, so a broken model stops its own dependents instead of poisoning them.

Verify

Finished running 4 data tests, 1 test ...

Completed successfully

Done. PASS=5 WARN=0 ERROR=0 SKIP=0 TOTAL=5

A WARN on test_obt is not a failure — it is the test doing its job. Query the OBT for the NULL key it found and decide whether the gap is a replication race or a real data problem.

Gold · Step 12

Gold: five dimensions that remember, one fact that does not

Gold turns the OBT into a small star schema. The two halves are built differently on purpose — and that difference is declared once, by directory, rather than repeated in every file.

01Ephemeral models shape each dimension — and never materialize

dbt/models/gold/ephemeral/ has one model per dimension, each a SELECT DISTINCT of that entity's columns off the OBT plus a *_gold_processed_at stamp:

dbt/models/gold/ephemeral/eph_customers.sqlsql · jinja
SELECT DISTINCT
    customer_id,
    customer_first_name,
    customer_last_name,
    customer_city,
    customer_updated_timestamp,
    customer_processed_at,
    CURRENT_TIMESTAMP() AS customer_gold_processed_at
FROM
    {{ ref('obt') }}

An ephemeral model builds nothing — no table, no view, not even a temp object. dbt inlines its compiled SELECT as a CTE wherever it is ref()'d, and it only exists in that context. eph_customers has no independent existence to query; it is a shaping step with exactly one consumer, so there is nothing to gain from materializing a throwaway table on the way to the dimension that actually matters.

Watch the grain: eph_orders excludes order_item_id

order_item_id is order-item grain, not order grain. Keeping it in a DISTINCT over order_id would produce more than one row per order for any order with multiple line items — silently violating dim_orders's unique_key: order_id below. Order-item grain belongs to fact_orders, never to a dimension.

02Snapshots turn those into SCD Type 2 dimensions

dbt/snapshots/dim_customers.ymlyaml
snapshots:
  - name: dim_customers
    relation: ref('eph_customers')
    description: Dimension Table for Customers
    config:
      database: tesco
      schema: gold
      strategy: timestamp
      unique_key: customer_id
      updated_at: customer_updated_timestamp
      dbt_valid_to_current: "to_date('9999-12-31')"
  • YAML, not a blockThis is the YAML snapshot config dbt-core added in 1.9 — no {% snapshot %} block in a .sql file, just relation: pointing at a ref().
  • strategy: timestampDiffs incoming rows against the last snapshot by comparing updated_at. A changed row gets a new version instead of overwriting the old one — that is what makes this Type 2 rather than Type 1.
  • dbt adds three columnsdbt_valid_from, dbt_valid_to and dbt_scd_id, on its own.
  • dbt_valid_to_currentGives the current version's dbt_valid_to an open-ended sentinel date instead of NULL, which BI tools querying valid_from <= x AND valid_to > x generally prefer.

Because eph_customers is ephemeral, relation: ref('eph_customers') does not point at a real table — dbt inlines the ephemeral model's compiled SQL directly into the snapshot's own query at compile time. dim_customers is the only physical object either produces.

03The fact table is a plain model

dbt/models/gold/fact/fact_orders.sqlsql · jinja
SELECT
    order_id,
    order_item_id,
    customer_id,
    product_id,
    store_id,
    employee_id,
    total_amount,
    quantity,
    unit_price,
    line_amount
FROM
    {{ ref('obt') }}

No {{ config(...) }} block at all. fact/ has no matching nested key in dbt_project.yml, so it falls through to the gold: block's own +materialized: table and +schema: gold, and lands as a real, queryable tesco.gold.fact_orders. Nothing downstream ref()s it into a further shaping step — it is the deliverable, at order-item grain, carrying a foreign key to each of the five dimensions.

04Materialization is centralized, not repeated

dbt/dbt_project.ymlyaml
models:
  tesco:
    silver:
      +materialized: table
      +schema: silver
    gold:
      +materialized: table
      +schema: gold
      ephemeral:
        +materialized: ephemeral

dbt's model config is path-based: the gold: block applies to every model under models/gold/, and a nested key matching a subdirectory name — here ephemeral: — overrides just that subtree. This is why none of the six gold model files carry a config() block at all: the split between "ephemeral shaping step" and "real table" is declared once, by directory. (The silver models each repeat their own config() because each has a different unique_key; nothing gold-side varies per model, so it never drops below the directory level.)

dbt run does not build snapshots

It builds models — the six silver models, the OBT and fact_orders — but not dim_customers and friends. Populate the dimensions with uv run dbt snapshot, or use uv run dbt build, which runs seeds, models, snapshots and tests together in DAG order. dbt build is the command to reach for once bronze exists: it is the only one of the three that touches every gold object in one pass.

Verify

terminalbash
cd dbt
uv run dbt build

Then, in Databricks, confirm the star schema exists and that the dimensions really are versioned:

Databricks SQL editorsql

Orchestration · Step 13

Hand the whole chain to Airflow

Everything so far has been commands you typed. One DAG turns them into a pipeline that runs itself — and stops the moment any stage fails, instead of building silver on top of a half-written bronze.

dbt_tesco_pipelinedag
databricks_ingest_cdc >> source_freshness >> silver >> silver_test
                      >> obt >> obt_test >> gold_ephemeral >> gold_dimensions >> gold_fact

A test step after every model stage, and the whole thing gated behind the Databricks job that lands bronze. The dependency chain is the point: source_freshness cannot run while bronze is still mid-write, and gold_fact cannot run against an OBT whose tests never passed.

01Start it

terminalbash
cd airflow
cp .env.example .env          # then add your Databricks credentials, see below
docker compose up -d --build

airflow/ is a second, independent compose project — its own docker-compose.yaml, its own .env, its own Postgres. That Postgres is Airflow's metadata database (task state, DAG runs) and has nothing to do with the raw_data database from step 4.

Add two variables that .env.example deliberately omits

airflow/.env.example does not list DATABRICKS_HOST or DATABRICKS_TOKEN. That is on purpose — a workspace host and a token are exactly the kind of value that should never end up example-shaped in git history, even as placeholders. Add both to airflow/.env yourself:

airflow/.envenv
DATABRICKS_HOST=your-workspace.cloud.databricks.com
DATABRICKS_TOKEN=dapi...

Change the job ID before your first run

airflow/dags/orchestrate.py passes the Databricks job ID as a plain integer literal: utils.trigger_databricks_job(job_id=1088290843715942). That is this repo author's job. Replace it with the ID of the pipeline job you created in step 7 — visible in the URL of the job page in your workspace — or the task fails immediately with a permissions error.

Hard-coding it is a known rough edge, not settled design. Moving it to .env or an Airflow Variable is the improvement to make if you are touching this file anyway.

02Logging in is not what most tutorials tell you

This stack runs command: standalone, which uses SimpleAuthManager and creates a user named admin with a random password, printed once to the container's logs on first boot:

terminalbash
docker compose logs airflow | grep -A1 "Password for user"

Missed it? It is still readable inside the container:

terminalbash
docker compose exec airflow cat /opt/airflow/simple_auth_manager_passwords.json.generated

The airflow / airflow login you have seen elsewhere belongs to the official compose file, which creates a fixed user through airflow-init. There is no such default user in Airflow 3.x standalone.

Verify

terminalbash

tesco_airflow            Up 40 seconds
tesco_airflow_metadata   Up 45 seconds (healthy)

Two containers, not eight — that is correct here, see below. Then open localhost:8080, log in as admin, and trigger dbt_tesco_pipeline by hand. All nine tasks should go green in order.

03Why two containers and not eight

Apache's own docker-compose.yaml defaults to CeleryExecutor and stands up eight services: postgres, redis, airflow-init, scheduler, dag-processor, api-server, triggerer and worker.

This repo runs the same logical components — scheduler, DAG processor, API server, triggerer — as sub-processes of a single container, via command: standalone with AIRFLOW__CORE__EXECUTOR: LocalExecutor. Three services disappear entirely:

  • redisLocalExecutor runs tasks as forked subprocesses of the scheduler itself, so there is no queue to broker.
  • airflow-workerNo separate worker fleet to dispatch to. This is the service you would add replicas of to scale out — with one DAG there is nothing to scale.
  • airflow-initstandalone runs the DB migration and admin-user creation inline on boot, rather than in a container that exits.

docker ps showing two containers instead of eight is really "no distribution layer", not "fewer components". The official compose earns its complexity the moment you have enough concurrent, heavy DAGs that one machine's CPU stops being enough.

04Triggering Databricks with the SDK, not a provider

databricks_ingest_cdc does not run bronze ingestion itself — the job already exists in your workspace. The task's only responsibility is to start that job and block the rest of the DAG until it finishes.

airflow/dags/utils.py does this with the databricks-sdk package directly, rather than the apache-airflow-providers-databricks operator package most tutorials reach for. There is no DatabricksRunNowOperator here:

airflow/dags/utils.pypython
def trigger_databricks_job(job_id: int):
    w = establish_databricks_connection()
    job_trigger = w.jobs.run_now(job_id=job_id)
    print(f"Databricks job triggered. Run ID: {job_trigger.run_id}")

    while True:
        job_run = w.jobs.get_run(run_id=job_trigger.run_id)
        lifecycle_state = job_run.state.life_cycle_state
        result_state = job_run.state.result_state

        if lifecycle_state in [
            RunLifeCycleState.TERMINATED,
            RunLifeCycleState.SKIPPED,
            RunLifeCycleState.INTERNAL_ERROR,
        ]:
            if result_state == RunResultState.SUCCESS:
                print("Databricks job completed successfully")
                return
            raise Exception(f"Databricks job failed. ... {result_state}")

        time.sleep(5)

Poll every five seconds until life_cycle_state reaches a terminal value; anything other than SUCCESS raises, which fails the Airflow task, so the DAG never reaches source_freshness on a failed or skipped run. establish_databricks_connection() raises ValueError immediately if either credential is missing, rather than letting the SDK fail later with something vaguer.

Editing airflow/.env needs down + rebuild, not up -d

Values from env_file: are baked into a container at creation, not re-read on every up. Add DATABRICKS_HOST after the container already exists, re-run docker compose up -d, and os.getenv keeps returning None — the task fails as though the file were still empty. Recreate it outright:

terminalbash
cd airflow
docker compose down
docker compose up -d --build

--build matters for a second, unrelated reason: if airflow/Dockerfile also changed, a plain down && up -d rebuilds the container from the old image and you get ModuleNotFoundError: No module named 'databricks' instead of the credentials error. down without -v keeps the named airflow_metadata volume, so DAG history and the generated admin password survive.

If you would rather use the official docker-compose.yamldeep dive

Fetch it directly rather than hand-copying — it is long and changes across versions. Swap the version for whatever airflow/Dockerfile's FROM apache/airflow:... line pins, so the compose file and the image agree:

terminalbash
curl -LfO 'https://airflow.apache.org/docs/apache-airflow/3.3.1/docker-compose.yaml'

Four things have to change, because the official file pulls the stock apache/airflow image rather than building this repo's Dockerfile:

  • Point it at a custom image. x-airflow-common.image must build from airflow/Dockerfile, or you add the same pip install "dbt-core<1.12" "dbt-databricks>=1.12.4" "databricks-sdk>=0.117.0" step. Without it, no service has dbt on its PATH.
  • Mount ../dbt:/opt/dbt on every service that touches it — not just one. airflow-dag-processor needs it to parse the DAG, and every worker replica needs it too, since CeleryExecutor cannot guarantee which worker picks up a task. Miss one and that worker fails with dbt: command not found.
  • AIRFLOW_UID is mandatory on Linux, not just recommended: echo -e "AIRFLOW_UID=$(id -u)" > .env before first boot, or the mounted directories end up root-owned.
  • Login becomes airflow / airflow by default — no log message to go find.

orchestrate.py and utils.py do not need to change. Neither BashOperator nor the SDK calls know or care which executor runs them — drop both files into the official compose's ./dags unchanged. The .env gotcha above still applies either way.

01The quality gate

terminalbash
uv sync --dev
uv run pre-commit install
uv run pre-commit run --all-files

CI runs exactly these hooks, so a clean local run means a clean pull request. sqlfluff lints the generated SQL too — which is why loader.py emits single spaces and no column-alignment padding. There is no test suite; the verification in this guide is the test.

02Two files you must never hand-edit

Generated

scripts/sql/raw_data/ddl.sql

Committed so schema changes appear in code review, but produced by loader.py. To change the schema, change the inference rules and re-run the loader.

Secret

dbt/profiles.yml and both .envs

Live credentials, git-ignored. Commit changes to the .example versions instead. If one leaks, rotate rather than rewriting history.

03What is still rough

  • The Databricks job ID in orchestrate.py is a hard-coded integer. It belongs in .env or an Airflow Variable.
  • There are no data-quality gates in CI — tests run in the DAG, not on a pull request.
  • The DAG has schedule=None: it runs when you trigger it. Give it a cron once you trust it.
  • Only two of the six silver models carry generic tests. Extending properties.yml to all six is a good first contribution.
